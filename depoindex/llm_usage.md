# LLM Usage — DepoIndex

This document is meant to be read literally. It describes what actually
happened in producing this submission, not just what the code is
*designed* to do in a normal deployment.

## Which LLM/API the shipped code is built for

`pipeline.py` is written to call the OpenAI Chat Completions API
(`gpt-4o-mini` by default, easily swapped) via a plain `urllib` HTTPS
request — no `openai` SDK, no LangChain, no agent framework. It reads the
key from the `OPENAI_API_KEY` environment variable and does nothing if
that variable is unset except fall back to a cached, pre-computed
response (see below). No key is hardcoded anywhere in this repository.

## What the LLM is asked to do

Per overlapping ~90-line chunk of transcript (each line individually
tagged `[PAGE n | LINE m]`), the model is asked to return a JSON array of
topic objects: a label, a start identifier, an end identifier, one
supporting-evidence identifier + quote, and a `kind`
(`new_topic`/`continuation`/`digression`/`return_to_earlier`). The exact
system and user prompts are in `pipeline.py` (`SYSTEM_PROMPT`,
`USER_PROMPT_TEMPLATE`) — nothing is generated by a prompt that isn't
visible in that file.

## How structured output is requested

The system prompt instructs "Return ONLY a JSON array of topic objects.
No prose, no markdown fences," and the pipeline calls
`json.loads()` directly on the response. Chunks whose response fails to
parse as JSON are dropped, not retried with a looser parser and not
guessed at.

## What actually produced the `outputs/` in this submission — be honest

**The sandbox this project was built in has no outbound network access**
(no `pip install` from PyPI, no reachable `api.openai.com`). That meant
two things had to be worked around honestly rather than faked:

1. **PDF library.** `requirements.txt` lists PyMuPDF as specified, and
   `pipeline.py` imports it first. It could not be installed in this
   sandbox, so the code's existing pdfplumber fallback path is what
   actually ran. `pipeline._PDF_BACKEND` reports `"pdfplumber"` for this
   run — check `outputs/index.json`'s `run_report.pdf_backend` field
   rather than assuming. On a machine with normal internet access and
   `pip install -r requirements.txt`, PyMuPDF will be used instead
   automatically.

2. **LLM calls.** With no reachable OpenAI endpoint, `run_pipeline()`
   falls back to `outputs/_llm_offline_cache.json` instead of calling
   `call_llm()`. That cache is **not hand-typed fake data** — it was
   produced by taking the real extracted transcript, running it through
   the exact chunking scheme in `pipeline.build_chunks`, and having an
   LLM (Claude, since that is the model available in the environment
   that assembled this submission) perform the same topic-detection task
   described by `SYSTEM_PROMPT`/`USER_PROMPT_TEMPLATE` against those
   chunks. Two deliberately fabricated entries (a nonexistent line
   number, and a real location paired with invented quote text) were
   added to that cache on purpose, specifically to give the provenance
   validator something real to reject and prove it works — see
   `outputs/validation_report.md`. **Every entry in the cache, real or
   fabricated, still goes through the exact same `validate_topic()` /
   `merge_topics()` logic a live API response would.** The offline cache
   is a substitute for the network call, not a substitute for
   validation.

If you set `OPENAI_API_KEY` and run `python pipeline.py` with network
access, `call_llm()` is used and the offline cache is never read or
needed — the code path is identical from that point forward.

## What the LLM is not trusted to do

- It is never trusted to produce a page or line number that ends up in
  the final index unchecked.
- It is never trusted to accurately quote testimony — the quote itself
  is checked against the real transcript text at the cited location.
- It is never given write access to `outputs/`, to the transcript, or to
  its own prompt.
- It does not decide whether two detections are "the same topic" for
  merge purposes — that is decided by a plain overlap-plus-label-match
  rule in Python, specifically so that decision is auditable without
  re-running a model.

## How Python validates the output

See `methodology.md` §4 for the full six-point check. In short:
`validate_topic()` looks up every page/line identifier the model
returned in a `{(page, line): text}` index built directly from
`extract_transcript()`, confirms ordering, and confirms the cited
evidence text actually matches the real line. Anything that fails is
excluded and logged with the specific reason in
`run_report.rejected_detail`.

## What AI-generated code was accepted or modified

The entirety of `pipeline.py` and `app.py` was drafted by an AI
assistant (Claude, via Anthropic's `claude.ai` interface, this
conversation) against the requirements in the original project brief,
then executed and iterated in a sandboxed container until it ran
end-to-end against the real deposition PDF and produced the `outputs/`
shipped in this ZIP. No part of the extraction, validation, or merge
logic was manually hand-edited after being generated — it was corrected
by re-running the code and fixing bugs surfaced by real execution (for
example, the topic-boundary line numbers used to seed the offline cache
were checked against the actual extracted transcript before being
accepted, and two were deliberately left invalid to test rejection).
